# Big-frame control panel: the per-command decision

**Card:** ARC-138 — "Big-frame control panel: make every command actually work, per device".
**Surface:** the action column of the big (floating) device frame, `apps/console/src/pages/ControlPage.tsx`.
**Rule being applied:** AGENTS.md section 7 — *"Render a control only when it performs its action: it either runs the operation and reports the true outcome, or it is not shown."*
**Premises re-derived on:** 2026-09-21, from the current rules, not from ARC-138's original quote of `handleDeviceAction`. AGENTS.md section 3 retired the blanket ban on a general device command on 2026-09-17, so no control on this panel is refused *because it is a device command*. Every deferral below names the capability that is actually missing.
**Owner ruling applied:** 2026-09-21 — **no control is removed.** Every one of the thirteen is COMPLETED: wired, working, per device, through the kernel. This record therefore no longer records a withdrawal, and a control that cannot act is not rendered only until the increment that wires it lands — each one below carries the surface it needs.
**Landed:** 2026-09-21 — the six device-command controls that were still to wire are now **DISPATCHES**, and so is **Quick Phrase**: all thirteen controls act. Nothing on this panel is withdrawn.

## The device-operations surface this increment added

Two RPCs rather than one, and the split is a safety property rather than a convenience:

- `RunDeviceOperation` (`RunDeviceOperationRequest`, `proto/drift/v1/device_operations.proto`) runs **one catalogued operation** on **one named device**. Its operation is a closed enum whose members map one-to-one onto reviewed catalog kinds (`internal/transport/connect/device_operations.go`), with `UNSPECIFIED` deliberately absent from the request table, so a request that names no operation is refused as malformed rather than resolved into one.
- `RunAdvancedCommand` runs **the operator's own argument array**. It is a separate entry point with a separate request type and no operation value that selects it, so a catalogued request cannot reach the advanced path and there is no request in which both could be named. Its array is validated by the recogniser that exists for it — the same one that decides what may reach an argv token — and never by the catalogued allow-list.

The device is named by **registry identity** on both. The serial an operation travels over is resolved by the application boundary from the registry's current-endpoint projection, so a caller cannot make the plane act at a transport it supplies. The refusal vocabulary travels as contract (`DeviceOperationRefusalReason`), because several distinct operator situations share one Connect code and a code-only mapping would collapse them into "something went wrong".

`DeviceOperationResult` is the one row shape both RPCs answer with, and it names the device, the operation, whether the operation was applied, **whether a read-back was taken at all** (`verified`), which refusal it was, what the device answered (`detail`) and the artifact an export stored. A surface renders that row; it does not reconstruct a story from a refusal token.

## Where a refusal reaches no device

Every wired command's refusal is the plane's own, produced before dispatch where the mechanism allows it, and the console states it where the operator is reading. The panel's own outcome line (`data-testid="panel-operation-outcome"`) carries the plane's row sentence — the summary is derived from the row, never a substitute for it.

Three distinctions the row keeps that a naive implementation would lose:

1. **"The device answered and it does not hold" is not "nothing was read".** A reading that states a refusal holds a device answer: a device that listed no enabled input method *answered the list*, and a file whose bytes were not admitted *was read off the device first*. Such a reading is published, so the row keeps its own reason rather than being flattened into `outcome_indeterminate`.
2. **The reason survives the hop.** The dispatch kernel reduces an adapter failure to an outcome and a class before a caller sees it, so the cause does not survive to the boundary that owns the row. The **reading** does: the applier states the refusal from the reading it took, which is the same object it states what the device answered from, so a row can never report one without the other.
3. **A refusal that reaches no device is decided before the device is resolved.** An unconfirmed array, a file name this product does not address and an artifact the workspace does not hold are all refused with their own reason and contact nothing — which the tests assert as a property (`the transport was issued nothing`), not as an absence of evidence.

## Quick Phrase — what it dispatches, and what it deliberately does not

It types text into the device through the kernel's typed-text action, which already exists and is already reachable. The console collects the phrase, registers the value once on its own content surface, and the dispatch names it by an **opaque handle**: the value is never a parameter that travels, and nothing about it is rendered back.

What this control does NOT add is a **durable phrase catalogue**, and that is the one part of this card that stays parked. The reference registry is in-memory, bounded, and releases a value at most once — it is explicitly not a store (`internal/edge/execution/text_reference_registry.go`), and AGENTS.md §184/§185 require content to be reached through an opaque handle and released at most once rather than persisted where it can render. A phrase an operator wants to *keep* is a content-at-rest decision about their own text, and the candidate home is the artifact store (§127 — bytes in the private content-addressed store, metadata only in SQLite). That is an owner ruling on where phrases live, not an implementation choice made inside this card, so the control dispatches and stores nothing until that ruling exists.
